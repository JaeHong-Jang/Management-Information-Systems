# 오케스트레이터 (orchestrator)

- 팀: 지휘 (lead)
- LLM 사용: 아니요. 규칙으로 실행한다.
- 앞뒤 에이전트: ask: 요청 진입 → 본인 → librarian / record: 요청 진입 → 본인 → privacy-guard / approve: 요청 진입 → 본인 → synthesizer / resolve: 요청 진입 → 본인 → privacy-guard / lint: 요청 진입 → 본인 → linter / train: 요청 진입 → 본인 → trainer

## 하는 일

요청을 여섯 흐름 중 하나에 배정한다.
설정에 적힌 순서로 에이전트를 실행하고 게이트 결과를 요약한다.

## 입력 / 출력

- 입력 `flow`: 실행할 흐름. 예: `ask`.
- 입력 `input`: 요청 내용. 예: `쿠폰 바코드가 읽히지 않아요`.
- 출력 `runId`: 실행 식별자. 예: `run-example`.
- 출력 `summary`: 실행 결과 요약. 예: `점장 답을 기다립니다`.

## 판단 규칙

1. 흐름은 ask·record·approve·resolve·lint·train 중에서 고른다.
2. 실행 순서는 해당 흐름의 steps 배열을 따른다.
3. ask는 인용·규정·표현 검증 뒤에 점장 연결을 실행한다.
4. record는 개인정보를 가린 뒤에 인터뷰와 카드 편집을 실행한다.
5. 게이트 실패를 성공으로 바꾸지 않는다. 실패 사유와 후속 처리를 남긴다.

## 하지 않는 일

LLM을 호출하지 않는다. 흐름 선택과 실행 순서는 규칙이 맡는다.
답변을 직접 쓰거나 점장 대신 사례를 승인하지 않는다.

## 실패하면

answer-gate 실패 시 근거 없는 문장을 빼고 다시 확인한다.
남는 문장이 없으면 점장에게 넘긴다.
card-gate 실패 시 막힌 표현을 표시하고 작성자에게 돌려보낸다. 저장 상태는 승인 대기로 둔다.

## 근거 이론

Aamodt & Plaza(1994)의 사례기반추론 4R을 흐름 설계에 적용한다.
검색·적용·수정·저장이 이어지도록 실행 순서를 묶는 역할이다.
이 역할 배정은 서비스 설계다. 논문이 특정 에이전트 구성을 제시한 것은 아니다.

근거 범위: 참고 노트 「06_선정아이디어_매장위키」의 3~5절.
이론은 역할의 설계 근거다. 이 하네스의 성능 검증 결과는 아니다.

## 신입이 체감하는 것

질문과 기록을 어디에 넣어야 할지 따로 고민하지 않는다.
