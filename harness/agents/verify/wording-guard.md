# 표현 검증 (wording-guard)

- 팀: 검증팀 (verify)
- LLM 사용: 아니요. 규칙으로 실행한다.
- 앞뒤 에이전트: ask: policy-checker → 본인 → escalator / record: card-writer → 본인 → 흐름 종료 / resolve: card-writer → 본인 → synthesizer

## 하는 일

답변과 사례 카드 문장을 금지 표현 정책과 대조한다.
일치한 표현과 차단 이유를 작성자나 게이트에 돌려준다.

## 입력 / 출력

- 입력 `text`: 검사할 문장. 예: `확인한 뒤 점장에게 보고한다`.
- 입력 `rules`: 금지 표현 정책. 예: `blame-customer` 규칙.
- 출력 `problems`: 일치 표현과 이유 목록. 예: `[]`.
- 출력 `status`: 검사 상태. 예: `ok`; 한 건 이상이면 `blocked`.

## 판단 규칙

1. 금지 표현 일치가 0건이면 이 검사에서 통과한다.
2. 1건 이상이면 blocked로 표시하고 정책의 why를 함께 남긴다.
3. 고객 비난·보상 단정·임의 무료 약속을 정책 정규식으로 검사한다.
4. 예외를 지우는 단정·AI 확신 표현·점장 보고 금지도 같은 정책으로 검사한다.
5. 정규식에 걸리지 않았다는 사실을 내용 전체가 적절하다는 보증으로 쓰지 않는다.

## 하지 않는 일

LLM을 호출하지 않는다. 일치 탐지와 차단 사유는 정책 규칙이 맡는다.
금지 표현을 몰래 순화해 원래 작성자가 동의한 문장으로 취급하지 않는다.

## 실패하면

ask의 answer-gate 실패 시 근거 없는 문장을 빼고 다시 확인한다.
남는 문장이 없으면 점장에게 넘긴다. 표현 문제도 재확인 대상으로 남긴다.
record의 card-gate 실패 시 막힌 표현을 표시하고 작성자에게 돌려보낸다. 저장은 승인 대기로 둔다.

## 근거 이론

참고 노트 5절은 위험한 예외를 점장에게 넘기는 설계를 제안한다.
표현 검사는 AI의 문장이 임의 보상이나 보고 차단 지시로 쓰이는 일을 막는 보조 장치다.
이는 서비스 설계 근거다. 노트의 논문이 이 정규식 정책의 효과를 검증한 것은 아니다.

근거 범위: 참고 노트 「06_선정아이디어_매장위키」의 3~5절.
이론은 역할의 설계 근거다. 이 하네스의 성능 검증 결과는 아니다.

## 신입이 체감하는 것

고객 응대에 그대로 쓰기 어려운 표현을 미리 확인한다.
