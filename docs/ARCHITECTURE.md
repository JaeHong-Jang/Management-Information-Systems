# 이어받기 설계

매장 하나의 예외 대응 지식을 사례 카드로 쌓는 위키와, 그 위키를 다루는 에이전트 팀. 현재 데모 구조와 통제 범위를 적는다. 배포 전 필요한 통제는 마지막 절에서 구분한다.

## 한 장 요약

```
숙련 직원 기록 ─▶ [수집팀] 개인정보 가드 → 회고 인터뷰어(왜?) → 사례 카드 편집자 → 표현 검증 ─▶ 승인 대기 카드
                                                                                            │ 점장 승인
신입 질문 ─▶ [답변팀] 검색 사서 → 현장 코치 ─▶ [검증팀] 근거 → 규정 우선 → 표현 ─▶ 점장 연결 ─┤
                                                     (answer-gate)                │ 근거 없음      ▼
                                                                                  └─▶ 점장 답 ─▶ 새 카드 (질문 → 카드: became)
[위키 관리팀] 종합 편집자(토픽 원칙 재작성) · 위키 점검관(상충·만료·중복·공백) · 훈련 코치(AI 없이 먼저 판단)
모든 실행 ─▶ 실행 버스(SSE /api/stream) ─▶ 화면: 에이전트 진행, 위키 변경 피드, 온톨로지 그래프 증분
```

| `data/` | `seed.json`(가상 데모 매장) · `wiki/`(자동 컴파일된 마크다운 위키: index · log · people · topics/) |

## LLM이 하는 일과 규칙이 하는 일

| LLM (Claude `claude-opus-5-5` 또는 로컬 Ollama `ax4-light`, 구조화 출력) | 규칙 |
|---|---|
| 회고 인터뷰어: 빠진 판단 이유·금지·호출 기준을 되묻는 질문 | 개인정보 가드: 전화번호·카드번호·고객 이름 가림 |
| 사례 카드 편집자: 기록을 카드 필드로 구조화 | 검색 사서: 조사 제거 후 2-gram BM25 |
| 현장 코치: 찾은 카드만 근거로 답 | 근거 검증: 없는 카드·검색되지 않은 카드 인용 차단, 근거 없는 줄 삭제 |
| 종합 편집자: 토픽 판단 원칙 3~5개 | 규정 우선 검증: 공식규정·현장노하우가 섞이면 규정 우선 안내 |
| 위키 점검관: 의미상 상충 찾기 | 표현 검증: 금지 표현 6종 |
| 훈련 코치: 신입 답 채점 | 점장 연결: 근거 없음·문제 줄 삭제 후 답 없음·호출 기준 해당 |
|  | 점검관의 만료·효과 낮음·중복·빈 토픽·승인 대기 |

LLM이 쓴 답은 같은 실행 안에서 규칙(검증팀)이 다시 확인한다. API 키가 없거나 호출이 실패하면 각 LLM 에이전트는 같은 모양의 결과를 규칙으로 만든다. 화면 상단과 실행 기록에 `규칙 모드` 또는 `rules(LLM 실패 대체)`로 표시한다. 그래서 키 없이도 전체 흐름이 돈다.

`LLM_PROVIDER=ollama`면 같은 `ask()`가 Ollama `/api/chat`에 zod 스키마를 JSON Schema로 바꿔 `format`으로 넘긴다. 응답은 같은 zod 스키마로 다시 검사하고, 어긋나면 규칙으로 대체한다. 실행 기록에는 `ollama`로 남는다.

로컬 7B 모델로 `scripts/compare_modes.ts`를 돌린 결과(`docs/judge/llm_vs_rules.md`): 되묻기 질문은 규칙보다 기록 내용에 맞게 구체적이었다. 반면 카드 편집에서는 직원이 말하지 않은 판단 이유("고객 만족을 최우선으로")를 지어내고, 금지 칸에 시스템 지시문을 옮겨 적는 경우가 있었다. 판단 이유는 모델이 채우지 말고 되묻기로 직원에게 받아야 한다는 설계 근거로 쓴다.

### 가상 손님 (시뮬레이션, 하네스 밖)

`backend/src/sim/customers.ts`. Nemotron-Personas-Korea 페르소나 한 명을 뽑아 상황·손님 말·신입 질문을 만들고 `flows.ask`에 넣는다. 13개 에이전트에 속하지 않는 시험 도구다. 주제는 코드가 무작위로 고른다(작은 모델은 예시 주제로 쏠렸다). 모델 출력이 칸을 비우거나 지시문을 옮기면 버리고 상황 틀 10개 중 하나로 대체한다. 첫 시뮬레이션에서 '종이 도장 쿠폰' 질문이 어미 조각('다·는데·해요')만 겹친 오트 우유 카드로 답해지는 오답을 찾았고, 검색 토큰에서 어미 조각을 빼고 최소 근거 점수를 3에서 3.5로 올려 고쳤다(회귀 테스트 추가).

## 지식 모델

- 사례 카드: 상황 · **판단 이유** · 대응 · 하면 안 되는 것 · 점장 호출 기준 · 출처(공식규정/현장노하우) · 상태(승인 대기/승인/반려/보관) · 만료일 · 재사용·도움·안 됨 횟수 · 출처 질문.
- 수명: 기록 → 승인 대기 → 점장 승인 → 사용(재사용·피드백) → 점검(만료·효과 낮음·상충) → 갱신 또는 보관. KCS의 지식 상태 흐름과 Karpathy LLM Wiki의 ingest · query · lint 세 동작을 따른다.
- 그래프 노드: 토픽 · 사례 카드 · 사람 · 질문 · 출처. 관계: 속함 · 남김 · 물음 · 근거로 씀 · 점장 답 → 카드 · 출처 · 상충 · 중복.
- 마크다운 위키(`data/wiki/`)는 바뀔 때마다 다시 컴파일된다. 사람도, 다른 LLM도 그대로 읽을 수 있다.

## 실시간

`Run`이 에이전트를 부를 때마다 `run-start · agent-start · agent-end · gate · wiki · run-end` 이벤트를 버스로 보낸다. `/api/stream`(SSE)은 새로 붙은 화면에 최근 300개를 재생한 뒤 이어서 보낸다. 프론트 `LiveProvider`는 `wiki` 이벤트의 노드·관계를 그래프에 바로 합치고(새 노드는 이웃 옆에서 나타나 자리 잡음), 실행이 끝나면 스냅숏을 다시 받는다. `매장의 하루 재생`(`/api/demo/play`)은 실제 흐름 8개를 차례로 돌린다.

## 검증

백엔드 테스트는 3차 반영 후 31개다. 아래는 테스트 범위와 기존 화면 검증 기록이다. 이번 문서 작업에서 재실행하지 않았으므로 새 통과 결과로 읽으면 안 된다.

- `backend`: `npm test` (Vitest, 규칙 모드) — 31개. 검색, 인용·규정·표현 검증, 개인정보 가림, 질문 순서, 점장 이관→재축적→재질문, 회고 인터뷰, 상충·만료·중복 점검, 승인 재검사를 다룬다.
- 2차 추가 5개: 무인용 ‘공식규정’ 문장 제거, 3만원 기준의 2만원·5만원 비교, 두드러기·때리려고 표현의 이관, 승인 대기 질문 유지와 승인 후 종료, ‘안 된다’ 사실 서술의 금지 분류 제외. 모든 안전 어휘와 화면 노출 경로를 검증한 것은 아니다.
- `frontend`: `npm run build` 통과, Playwright로 10개 화면 캡처(1440px) 콘솔 오류·가로 넘침 0, 하루 재생 중 화면 4회 캡처로 실시간 반영 확인.

## 한계

- 데모 매장과 사례는 가상이다. 실제 매장 효과는 측정하지 않았다.
- 한국어 검색은 형태소 분석 없이 2-gram이라 동의어(예: 포스/POS)는 일부만 잡는다.
- 규칙 모드의 회고 인터뷰·카드 구조화는 문장 단위 휴리스틱이다. LLM 모드와의 품질 차이는 측정하지 않았다.
- 사람 계정·권한은 없다. 화면 위 `지금 사용하는 사람`으로 역할을 바꿔 시연한다.

## 통제 범위

이번 변경 설명은 전달받은 코드 변경 목록에 한정한다. 이 문서 작업에서는 코드를 수정하거나 동작을 재검증하지 않았다. 아래 통제는 답의 사실 여부나 실제 매장 운영의 안전성을 보장하지 않는다.

### 지금 데모가 실제로 막는 것과 지원하는 처리

| 대상 | 현재 통제·처리 |
|---|---|
| 만료·상충 근거 | 만료·상충 카드를 답변 근거에서 제외한다 |
| 무인용·허위 인용·금지 표현 | 해당 줄을 삭제한다. ‘공식규정’이라는 말이 있어도 근거가 없으면 삭제한다. 남는 답이 없으면 점장에게 이관한다 |
| 최종 출력 관문 | 신입에게 답을 보내기 직전 금지 표현 줄과 이유를 다시 검사한다. 안전 이관 답에는 매장 사례 행동을 붙이지 않는다 |
| 점장 호출 조건 | 금액 기준은 숫자로 비교한다. 3만원 이상 기준에 2만원 질문은 해당하지 않고, 5만원은 점장에게 이관한다 |
| 안전 어휘 안전망 | `harness/policies/forbidden-phrases.json`의 `alwaysEscalate`로 건강 이상·부상·폭력·시설 위급·범죄 의심 어휘를 검사한다. 해당 질문은 위키가 답하지 않고 점장에게 넘기며 119/112를 안내한다. 두드러기·미끄러짐·때리려고 같은 표현도 포함한다 |
| 입력 개인정보 | 질문·기록·점장 답의 개인정보를 실행 기록·저장 전에 가린다 |
| 점장 답 게시·승인 | 점장 답에 금지 표현이 있으면 승인 대기로 저장하고 신입에게 보여 주지 않는다. 승인 때 표현을 다시 검사하며, 카드가 승인될 때 질문을 닫는다. 고쳐서 승인한 점장 답은 승인된 카드 내용으로 다시 만든다. 수정 전 원문은 보여 주지 않는다 |
| 대기 질문 | 비슷한 대기 질문을 자동 해결한다. 조건이 다른 질문의 오처리 여부는 별도 검증이 필요하다 |
| 지표 해석 | 분자·분모와 시드 제외 보기를 제공한다. 실제 매장 성과를 입증한 것은 아니다 |
| 업무 진입 | 역할별 첫 화면을 제공한다. 역할 선택은 인증이 아니다 |
| 갱신·상충 정리 | 갱신 전에 내용을 확인한다. 상충 카드는 나란히 비교하며, 공식규정 카드를 보관할 때 확인과 사유 입력을 받는다. 보관 사유는 서버에 저장한다. 공식규정 원문이 없으면 ‘규정 원문 미첨부’를 표시한다 |
| 기록 부담·공개 선택 | 기록 임시 저장을 제공한다. 크레딧을 끈 카드는 ‘이름 비공개’로 연결한다. 변경 기록·마크다운 위키·카드 상세에도 비공개 선택을 적용한다. 근무 외 기록 강요를 기술적으로 막는 것은 아니다 |
| 질문자 표시 | 그래프에서는 신입들 같은 역할 묶음으로 표시한다. 개요와 위키 사람 페이지에서 개인별 질문 수를 세지 않는다 |
| 규칙 모드 카드 편집 | 금지 판정을 ‘하지 않/하지 말/금지/절대/면 안 된’으로 좁혔다. ‘안 된다’는 사실 서술만으로 금지 칸에 넣지 않는다 |
| 실행 기록·화면 | 화면 진입 점검은 실행 기록을 남기지 않는다. 오케스트레이터 요약에는 한국어 에이전트 이름을 쓴다. 질문의 이유는 답 아래에 펼치고 카드 번호는 답 끝에 한 번 표시한다. 안전 상황은 경고 상자로 보인다 |
| 기록·점장·훈련 안내 | 규칙 모드의 되묻기는 ‘기본 질문’으로 표시한다. 점검 결과는 기본으로 접는다. 훈련은 실제 사례의 상황 그대로 출제하며 ‘무엇을 할지·왜·하면 안 되는 것’을 쓰도록 안내한다 |

### 막지 못하는 것

계정·권한이 없어 승인자가 실제 점장인지 확인하지 못한다. 공식규정 원문 첨부 기능은 미구현이다. 원문과 버전을 확인하지 않는다. 출처 배지가 규정의 권위를 보증하지 않는다. 인용 카드가 유효해도 문장이 카드 내용을 정확히 설명하는지, 내용 자체가 사실인지는 검증하지 못한다. 개인정보 가림도 모든 식별정보를 탐지한다는 뜻은 아니다.

안전 어휘 안전망은 목록에 없는 표현을 놓칠 수 있다. 금액 비교를 추가했어도 모든 부정·복합 조건을 해석하는 것은 아니다. 답의 이유와 이관 후 임시 행동까지 의미가 안전한지 보장하지 않는다.

개인별 질문 수를 표시하지 않아도 질문 기록에는 ‘내가 물은 질문’을 위한 `askerId`가 저장된다. 계정·권한이 없어 접근 통제를 하지 않는다. 크레딧 비공개는 저장된 신원의 익명화를 뜻하지 않는다.

규칙 모드는 제한된 표현과 패턴에 의존한다. 회고의 맥락, 빠진 조건, 동의어를 충분히 다루는지는 검증이 필요하다. LLM 모드의 품질·비용은 여전히 미실측이다. API 키가 생기면 `backend/scripts/compare_modes.ts`로 비교할 예정이다.

### 실제 매장 배포 전 필요한 통제

| 통제 | 배포 전 정할 것 |
|---|---|
| 로그인·역할 권한 | 신원을 확인하고 질문·기록·승인·갱신 권한을 서버에서 검사한다 |
| 매장별 데이터 분리 | 조회·검색·저장·실행 기록의 매장 범위를 검사한다. 다른 매장 자료 접근을 차단하는지 검증한다 |
| 공식규정 원문·확인자 | 원문 첨부, 버전, 적용 범위, 확인자를 기록한다. 개정 때 연결된 사례를 재검토한다 |
| 보관 기간 | 질문·사례·임시 기록·실행 기록별 보관 기간과 삭제 책임자를 정한다. 백업 삭제 범위도 정한다 |
| 모델 호출 로그 보존 정책 | 호출 입력·출력 중 남길 항목, 가림 시점, 접근 권한, 보존·삭제 기준을 정한다. 외부 모델 제공자의 보관 조건도 확인한다 |

근무시간 내 기록, 질문자 개인 통계 없음, 평가 목적 사용 금지는 파일럿 운영 원칙으로 확인한다. 임시 저장이나 크레딧 선택만으로 그림자노동 문제가 해결됐다고 판단하지 않는다.
