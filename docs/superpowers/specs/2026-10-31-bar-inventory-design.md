# 술집 재고·발주 설계

2026-10-31. 데모 매장을 카페에서 술집으로 바꾸고, POS 판매 기록으로 재고와 발주 시점을 계산하는 기능을 이어받기에 더한다. 숫자는 규칙이 계산하고, 숫자를 바꾸는 이유는 사례 카드에서만 가져온다.

## 결정

| 항목 | 결정 |
|---|---|
| 데모 매장 | 카페 온새미로 → 술집 「포차 달빛」(가상). 카페 시드는 기존 테스트 31개의 고정 자료(`backend/test/fixtures/cafe-seed.json`)로 남긴다 |
| 판매 입력 | POS 매출 CSV 업로드. 열 이름 변형(판매일자·영업일자 / 상품명·메뉴명 / 판매수량)과 UTF-8·EUC-KR을 받는다. 엑셀(xlsx)은 CSV로 저장해 올린다 |
| 메뉴 → 재료 | 메뉴별 소모량표. 처음 보는 메뉴는 레시피 편집자(AI)가 초안을 내고 점장이 승인한다. 승인 전 메뉴는 사용량에 넣지 않는다 |
| 예측 | 최근 4주 요일별 평균 × 승인된 보정 배수 |
| AI 분석 | 다가오는 매장 일정과 승인된 재고 카드를 비교해 보정 제안을 낸다. 제안은 카드를 인용해야 하고, 배수가 카드 글에 있어야 한다(근거 검증). 점장이 승인해야 예측에 들어간다 |
| 재고 실사 | 마감 때 센 값을 넣는다. 계산과의 차이가 주간 평균 사용량의 10% 이상이면 점장 할 일 |
| 발주 | 주문서 초안까지. 거래처별로 묶고 줄마다 이유를 단다. 실제 주문은 사람이 하고 '보냈어요'로 표시하면 입고 예정으로 계산한다 |

## 계산 (규칙)

- 일별 사용량 = Σ(메뉴 판매 수 × 승인된 메뉴별 소모량)
- 요일별 평균 = 오늘 전 28일 중 같은 요일 평균. 같은 요일 자료가 2개 미만이면 전체 일평균. 판매 기록 기간에 그 요일이 두 번 넘게 지나갔는데 한 번도 안 팔렸으면 쉬는 요일(0)
- 예측 사용량(날짜) = 요일별 평균 × 그 날짜에 걸린 승인 보정 배수
- 지금 재고 = 마지막 마감 실사 + 그 뒤 입고 − 그 뒤 사용량 (실사는 그날 마감 후 값, 입고는 그날 영업 전 도착. 같은 날이면 기록 시각으로 앞뒤를 가려 마감 실사 뒤 입고 확인은 다음 영업에 쓴다). 마지막 판매일 뒤 POS를 아직 안 올린 날은 요일별 평균 × 보정으로 추정한다
- 남은 일수 = 예측 사용량을 하루씩 빼서 0이 될 때까지
- 주문일 = 재고 위치(영업 시작 재고 + 보냈지만 아직 안 온 주문)가 발주점 이하가 되는 첫날. 오늘 마감 실사가 있으면 예측은 내일부터 시작하고, 내일 영업 시작에 발주점 아래면 오늘 주문이다
- 권장 주문량 = 적정량 + (도착 후 7일 안 승인 보정으로 늘어난 예측 사용량) − 도착일 예상 재고, 발주 단위로 올림, 최소 1단위
- 추천 기준값 = 발주점 일평균 × (리드타임 + 1), 적정량 일평균 × 7
- 사용량 이탈 = 최근 7일 실제가 그 전 3주 요일별 평균 기대치와 30% 이상 차이
- 실사 차이 = 실사 값 − 그 실사 시각의 계산 재고. 저장해 둔 값이 아니라 점검 때마다 다시 계산한다(그날 POS를 나중에 올리면 풀린다). 앞선 실사가 없으면 비교하지 않는다

## 하네스

재고팀 4명을 더한다.

| 에이전트 | 하는 일 | 방식 |
|---|---|---|
| POS 정리원 | CSV에서 날짜·메뉴·수량을 뽑고 처음 보는 메뉴를 찾는다 | 규칙 |
| 레시피 편집자 | 처음 보는 메뉴의 소모량 초안. 규칙 대체: 이름이 겹치는 기존 메뉴의 소모량을 복사하거나 품목명과 같으면 1개 | LLM |
| 수요 분석가 | 요일별 평균 계산, 일정·카드로 보정 제안. 규칙 대체: 일정 이름으로 재고 카드를 검색하고 카드에 적힌 배수만 쓴다 | 규칙 + LLM |
| 발주 담당 | 오늘 주문할 품목을 거래처별 주문서 초안으로 | 규칙 |

흐름: `pos`(POS 정리원 → 레시피 편집자 → 수요 분석가 → 근거 검증 → 발주 담당), `stocktake`(발주 담당 → 위키 점검관), `stockapprove`(레시피·보정 승인, 입고 확인 → 발주 담당). 게이트 `adjust-gate`: 근거 없는 보정은 버린다(카드 없음·다른 품목 카드·카드에 없는 배수·날짜 형식·매장 일정 밖 기간). 반려한 보정은 다시 제안하지 않는다.

## 위키 연결

- 카드에 `itemIds`를 더해 품목과 잇는다. 그래프에 품목 노드와 카드 → 품목 관계를 더한다.
- 신입 질문에 품목과 매장 주문 의도("몇 짝 시켜야", "남았어요", "주문해요?")가 있으면 발주 담당이 `[재고 현황]` 줄을 답 맨 위에 붙인다. 숫자는 코치(LLM)가 쓰지 않는다. 카드 답과 점장 호출은 그대로 둔다. 근거 카드가 없거나 다른 품목을 가리키는 카드뿐이면 재고 숫자로만 답하고 점장에게 넘기지 않는다. 손님 주문("더 시킬 때")이나 품절 대응("떨어졌을 때")은 주문 의도로 보지 않는다.
- 남은 일수가 리드타임보다 짧은 품목이면 그 품목에 연결된 품절·대체 카드를 함께 보여 준다.
- 점장 할 일에 재고 차이 · 사용량 이탈 · 레시피 대기 · 보정 제안을 더한다. 재고 차이에 점장이 남긴 이유는 재고·발주 토픽 카드가 되어 다음 점검 때 함께 보인다.

## 화면

관리 묶음에 「재고·발주」(`/inventory`). 첫 문장은 "오늘 주문할 품목 N개". POS 파일 올리기, 마감 재고 세기, 품목 표(남은 양·남은 일수·주문일·권장량·보정), 품목 상세(요일별 사용량, 기준값 수정, 연결 카드), 주문서 초안(복사, 입고 확인), 레시피·보정 승인. 대시보드에 오늘 주문 요약 한 줄.

## 테스트

규칙 모드 Vitest. CSV 파싱(열 이름 변형, EUC-KR, 취소 수량), 사용량·요일별 평균, 주문일·권장량 올림, 보정 근거 검증(카드 없음·배수 불일치 차단), 실사 차이 → 할 일, 질문에 재고 현황 붙이기, 술집 시드 검색.

## 하지 않는 것

POS API 실시간 연동, xlsx 직접 읽기, 날씨 연동, 자동 주문 전송, 다매장. 필요해지면 따로 설계한다.
